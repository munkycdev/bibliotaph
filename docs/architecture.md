# Bibliotaph architecture

This describes the design of Bibliotaph 1.3. For what the app does, see [features.md](features.md); for how to use it, the [user guide](guide/getting-started.md).

## At a glance

Bibliotaph is one WPF app on .NET 11. PDFium runs in a small pool of isolated worker processes; e-books are read by managed code in the app. The user's work lives in one SQLite file and a rebuildable search index in another, searched with FTS5, and an in-process durable job queue reads the library in the background. Bibliotaph catalogs files where they are and never writes to a source file.

## Key decisions

| Decision | Why |
| --- | --- |
| .NET 11, self-contained, per-user | Its support runs to November 2028, the same as .NET 10 LTS; self-contained means nothing to install first. |
| One UI process plus PDFium worker processes, each in a job object | A slow, damaged or hostile PDF being indexed can't stall the page being read or crash the app. |
| Two SQLite files: `catalog.db` (user work) and `index.db` (derived) | "Rebuilding the index never touches the user's work" is a physical fact, not a convention. |
| EF Core for `catalog.db`; Microsoft.Data.Sqlite with Dapper and prepared commands for `index.db` | FTS5's `MATCH`, `bm25()`, `snippet()` and `highlight()` have no LINQ translation, bulk page inserts need prepared commands in batched transactions, and `index.db` has no migrations. |
| SQLite FTS5 for search (bm25, unicode61, diacritics removed) | Fast enough for a large personal collection, with no second storage engine. |
| E-books cut into pages by a fixed rule over their content, read in the app process by managed code | Search, evidence, notes and binders all point at pages, so an e-book needs pages that never move: a rule over the file's content gives the same pages on every PC, unlike pages laid out by a renderer. There is no native library to contain, so no worker process; size limits guard against hostile archives instead. |
| Windows.Media.Ocr, inside the index worker | Ships with Windows, so no native binaries or language data to package; in a comparison it was as accurate as Tesseract and 7 to 14 times faster. |
| An in-process, durable job queue in `index.db` | Processing runs only while the app is open; a small scheduler is easier to reason about than a framework. |
| WPF with CommunityToolkit.Mvvm and the generic host; a custom theme, no control suite | The design is a bespoke editorial look, not Fluent. |
| AI local first: a built-in llama.cpp engine or an OpenAI-compatible server (Ollama, LM Studio), never a cloud fallback | Book text stays on the machine and costs nothing per book. AI is optional and only suggests. |
| Content identity is SHA-256 of the whole file, with NTFS file IDs to spot moves | Duplicates, moves and revisions fall out without special cases; disk reads, not the hash, dominate the cost. |
| Online libraries through the real site in WebView2 | The user signs in on the service's own page; Bibliotaph keeps no password and reads only what the page shows. |
| Library sync through per-PC files in a folder the user picks | A second PC gets the same work with no sync service and without syncing a live database. |
| Velopack installer and updates from GitHub Releases | Per-user install with no admin, delta updates, and it works with an unpackaged WPF app and native PDFium binaries. |
| GPL-3.0-or-later, with permissive or GPL-compatible dependencies only | The app is free software, and every shipped component can be redistributed under it. |

## Process model and isolation

| Process | Does | Why there |
| --- | --- | --- |
| `Bibliotaph.exe` | Shell, view models, catalog and index access, search, the job scheduler, classification, backup, sync | One process owns the databases, with no IPC for ordinary work. |
| `PdfWorker.exe`, viewer workers | Open, render, tile, find on page, character boxes and links for the books being read | One per reader window showing a PDF, up to three; more windows share the least busy. A reader never shares a worker with indexing. |
| `PdfWorker.exe`, index worker | Probe, page text, covers, OCR of flagged pages, reading a download being checked | OCR needs a rendered bitmap; keeping it beside PDFium keeps large bitmaps out of the app. |
| `aiworker\llama-server.exe` | The built-in AI's model, only while it has work | A native crash or running out of graphics memory takes down only that process. |

`PdfWorkerPool` (Pdf.Host) starts workers on first use and stops a viewer worker when its last reader lets it go. Each worker talks length-prefixed JSON messages over a named pipe and returns pixels through a shared memory section, which the viewer copies into a frozen bitmap. Each runs in its own job object that caps committed memory (1.5 GB for a viewer worker, 1 GB for the index worker), allows one process and no children, and kills the worker if the app dies. A request that times out kills and restarts the worker. `PoisonTracker` remembers which file and page killed a worker; after two kills on the same page the work is refused with that reason, so one bad book can't loop the queue.

Indexing reaches PDFs only through `IPdfEngine` (Pdf.Contracts): open a file, then read its pages' text, draw a page, or OCR one. On Windows that is `WorkerPdfEngine` (Pdf.Host) over the index worker, which opens the document again if the worker restarted. The seam is there so the stages can run where the worker can't, such as a web version with PDF.js; such an engine answers `OcrUnavailable` for OCR it doesn't have, which blocks the OCR stage with a reason. Engine failures are `PdfEngineException`s, the worker's included: the lane retries the job unless the exception says trying again can't help, as for a page that has killed the worker twice. The viewer still uses the pool directly.

The worker opens a PDF through `FPDF_LoadCustomDocument` over a read-only .NET stream, so PDFium never sees the path (names outside the ANSI code page open like any other) and the file is never opened for writing.

## Storage

Everything lives in `%LOCALAPPDATA%\Bibliotaph\`, never in a synced folder. Both databases run in WAL mode; the UI reads through separate connections, and all writes to `index.db` go through one writer that batches pages into transactions.

| File | Holds | On schema change |
| --- | --- | --- |
| `catalog.db` | Everything the user made or decided, and what can't be derived again | An EF Core migration, after an automatic `VACUUM INTO` copy |
| `index.db` | Everything derived from files or projected from `catalog.db` | An additive change runs its embedded `upgrade-N.sql` in a transaction (schema version 19); anything else, or a failed upgrade, drops the file and rebuilds it, re-queuing documents by content hash |
| `cache\` | Covers by content hash; page thumbnails per book (`cache\pages\`, trimmed past 256 MB, least recently opened first); files extracted from ZIPs (`cache\extract\`, trimmed past 5 GB); site icons | Deleted freely; never backed up |

Beside them are `backups\`, `logs\`, the covers users chose for books owned elsewhere (`covers\`, which nothing could rebuild), the WebView2 profiles (`browser\` for online libraries, `ebook-reader\` for the e-book reader), the built-in AI's downloaded engine (`engine\`) and models (`models\`).

### catalog.db

- **Files and documents.** `source_root` (path, volume serial, availability), `file_location` (root, relative path, size, modified time, NTFS file ID, content hash, state: present, missing or online-only; a file inside a ZIP points at its ZIP and records its entry path and CRC) and `document`, one row per distinct content (hash, format, page count, capabilities, protection, and the page the user chose as its cover).
- **Entries.** An `entry` is what the library lists and the user catalogs: a whole document, a part (an adventure inside a file), a pack of images, or a book owned elsewhere with no file. `entry_source` says which documents an entry shows, with a page range for a part, and which is current. Joins (`entry_join`) record the rows they moved, so Undo and "Not the same book" can move them back. `copy_decision`, `version_proposal`, `elsewhere_match`, `pack_decision` and `part_proposal` remember the user's answers to Match, packs and parts, so nothing is asked twice.
- **Metadata.** `assertion` holds every value with its origin (embedded, folder, file name, rule, folder rule, user tag, AI, user), evidence pages and quote, run and state. The effective value is computed from it, never stored over it. `rejection`, `vocabulary_term`, `vocabulary_alias`, `ignored_folder_label`, `folder_rule`, `user_tag`, `correction_request`, `classification_run` and `chapter_scan` (a whole-book scan's chapters and findings, by content hash) sit beside it, so a rebuilt index never loses a model's evidence or the record of what was read.
- **The user's own things.** `favorite`, `reading_state`, `collection` and `collection_item`, `collection_folder` (folders made into collections, or declined), `collection_decline` (books declined for a collection), `smart_view` (saved searches), `pin`, `note`, `session_pack`, `session_section` and `session_item` (binders), `page_ref`, `ask_turn` (Ask this book conversations), `setting` and `sync_state`.

A `page_ref` is a page range on a document, with the printed label and page fingerprint of its first and last pages, so binder items and page notes can be found again in another copy or version.

### index.db

Pages, OCR word boxes, outlines, per-stage status and jobs are keyed by document. `page` holds each page's text, printed label, size, text quality and fingerprint; `page_fts` is an external-content FTS5 table over its text; `page_vec` holds Ask's page vectors, tagged with the embedding model and text version, and dropped by triggers when a page's text changes. `chapter` and `chapter_tag` hold the chapters of books the AI read whole and what it found in each, projected from `chapter_scan`.

What the library lists is keyed by entry and projected from `catalog.db` by `MetadataProjector`: `entry_doc` (the document an entry shows, its kind, copies and cover), `entry_member` and `member_fts` (a pack's images), `entry_meta` (effective title, labels, levels, players and review counts), `entry_facet` (closed field values behind the filter panel and field search), `term_alias`, `entry_fts` (the Documents tab's columns, including notes), `entry_ai` (which entries a model has read), and the user's marks: `entry_scope` (favorites, collections, binders), `scope_name`, `entry_note` and `entry_opened`.

Projection runs after hints, user edits, classification, packing and sync, and once at startup in the background, one projection at a time. A heart or an open projects only the marks. Because metadata is projected again at every start, an index rebuild loses nothing the user did.

## Files, identity and the processing pipeline

A document is a content hash; a path is where that content was last seen. Two paths with the same hash are copies of one document, a path that moves keeps its document, and new content at a path is a new document.

### Discovery and reconcile

A full scan runs at startup and on demand, and a `FileSystemWatcher` per root feeds the same reconciler while the app is open, debounced until size and modified time settle. A path whose size, modified time and NTFS file ID are unchanged isn't hashed again. A new path whose file ID, size and time match a location that left its own path is that file moved, and keeps its card. Where the disk keeps no file IDs (FAT, exFAT), a file that left one path and arrived at another in the same scan, with the same name, size and time, is taken as moved when nothing else could pair with either; anything ambiguous is hashed and finds its card by content.

Where a root lives is behind interfaces, so the scan and reconcile can run against a drive that isn't a Windows folder, such as a cloud drive in a web version. `ISourceLister` lists a root without opening a file: every file with its size, time and whether it is online-only, and the folders it couldn't read. On Windows that is `FileSystemSourceLister`, which doesn't follow links and leaves out folders that are roots of their own. `SourceScanner` then decides which files are read and counts the rest, the same for any lister. Files are opened through `ISourceFileReader`, disks and file IDs come from `IFileIdentity`, and changes from `IFolderWatcher`. Library paths stay strings: another drive mounts as a rooted path of its own, such as `/onedrive/<drive id>/Books`, with its item IDs as file IDs and its drive ID as the volume serial, so the catalog, the reconciler and library sync don't change.

An unreachable root, or one whose volume serial changed, goes offline as a whole; its files are never marked missing because of it. Opening a book whose file can't be reached shows a prompt that names the drive or the last folder, with a rescan to find it.

### ZIPs

A ZIP is read in place through the read-only reader with System.IO.Compression and never unpacked beside itself. The ZIP is a location with a hash and no document; each PDF or image inside is a location of its own, hashed as it is decompressed, and joins documents by hash like any file, so a book both loose and zipped is one document and the loose file is preferred. A ZIP saved again keeps the hashes of members with the same name, size and CRC, and a moved ZIP isn't read again. Stages and the viewer get a member extracted to `cache\extract\` and checked against its hash. A member that can't be read (a nested ZIP, a password, too big, damaged) is listed in Files needing attention.

### E-books

An EPUB is a document like a PDF: hashed, joined by content, found in ZIPs (an `.epub` is itself a ZIP, but is never listed as an archive of members) and never written to. Probe, Text and Covers read it in the app process through `EbookFiles` (Processing) and `EpubBook` (Ebooks), over the read-only reader's stream; OCR never runs on it.

- **Package.** `META-INF/container.xml` names the package; its metadata, manifest and spine give the title (the one refined as main), authors, publisher, date, ISBN (by check digit), subjects, description, reading order and fixed layout. The contents come from the EPUB 3 navigation document, else the EPUB 2 NCX, and become the outline. The cover is the manifest's `cover-image`, else EPUB 2's `<meta name="cover">`, else the first image of the guide's cover page or the first chapter.
- **Pages.** `EbookPaging` cuts the book into pages, which `page` stores as it stores a PDF's (`pdf_page` is the page's index, `text_source` is `pdf`, the file's own text, and the size is a nominal 6 by 9 inches). A fixed-layout book has a page per spine item. A book that marks its printed pages (a page list whose entries resolve, else `epub:type="pagebreak"` or `role="doc-pagebreak"` markers, at least 3) has those pages with their labels, what comes before the first cut as below. Otherwise each spine item starts a page, and a page ends before the block (paragraph, heading, list item, table row) that would take it past 2,500 characters, or before a heading once it holds 1,250; a longer block is split after a sentence. Each page starts at a locator (chapter, block, character), which the reader will use to show it. The rule depends only on the file, so page numbers are the same on every PC; `EbookPaging.Version` records it, and changing it would move every place that points into an e-book.
- **Text.** AngleSharp's HTML5 parser reads each chapter, after closing XHTML's self-closed elements (`<a id="x"/>`), which an HTML parser would otherwise leave open. Scripts, styles and SVG are skipped, nesting deeper than 256 is read as plain text, and the regular expression that closes elements doesn't backtrack.
- **Metadata.** The package's title and authors fill the fields a PDF's document information does, its publisher and subjects go with the keywords (matched against the vocabulary) and its description is the subject (where levels and party sizes are looked for), so rule hints treat both formats alike.
- **Limits.** Bytes actually decompressed are counted, whatever the archive claims: at most 64 MB an entry, 512 MB a book and 20,000 entries. XML is read with DTDs ignored, no resolver and no entity expansion.
- **Kindle books.** `Ebook.Open` tells formats by their bytes: a ZIP is an EPUB, a Palm database of type `BOOKMOBI` is `MobiBook`, and KFX (`\xeaDRMION\xee` or `CONT`) and Topaz (`TPZ`) are refused with a reason. `MobiBook` reads record 0's PalmDOC, MOBI and EXTH headers (title, authors, publisher, description, ISBN, subjects, date, language, cover, fixed layout), and prefers a KF8 version (version 8 in record 0, or the record EXTH 121 names in a file with both). Text records are decompressed (PalmDOC LZ77, or HUFF/CDIC with a nesting limit), their trailing entries cut by the extra-data flags, within the same byte limits as an EPUB. KF8 text is cut into flows by FDST; the HTML flow is put back into its files from the skeleton and fragment indexes (INDX records, their TAGX tags and CNCX strings), and the other flows become stylesheets and SVG. An older book's one HTML text is cut into parts at `<mbp:pagebreak>`, with empty parts joined to the next. Links by position (`filepos`, `kindle:pos:fid:off`) and the contents index's positions get ids at those places (the element starting there, or an empty anchor), `kindle:embed` and `recindex` become image and font paths numbered from the first resource record, and `kindle:flow` the flow files. Without a contents index, an older book's contents are the links on the page its guide names. The parts' paths are made up (`part0000.html`, `image00001.jpg`), so paging, indexing and the reader treat it as an EPUB through `IEbook`. A non-zero encryption field is DRM, read as protected like an EPUB's.
- **DRM.** An EPUB whose spine is listed in `META-INF/encryption.xml` under anything but font obfuscation (IDPF or Adobe), or whose encryption list can't be read, is protected: Probe records its package (so the card has its title and authors) with protection Unsupported, and Text fails with `TextAccessReasons.ProtectedEbook`, which the library reads as Protected.

- **Reader.** The viewer cuts the book again on open (the same rule, so the same pages) and `EbookReaderDocument` builds one HTML page of it: a `<section>` per spine item and an empty `<bt-page>` marker where each page starts, placed from the page's locator (splitting a text node for a page that starts inside a block). The book's HTML is cleaned on the way: scripts, styles, frames, forms, objects and media are dropped, attributes are an allowlist, ids are prefixed per chapter and internal links rewritten to them, web links kept for the app to open, and images point at `/res/` paths. A fixed-layout book gets a sandboxed `<iframe>` per page, sized from its viewport, whose page is cleaned the same way and keeps its stylesheets.
- **Browser.** `EbookView` shows that page in WebView2 (`WebView2CompositionControl`, so the reader's notices draw over it) with a profile of its own (`ebook-reader\`), at `https://book.bibliotaph.invalid/book.html`. Every request the page makes goes through `WebResourceRequested`: the page, the book's pictures, fonts and stylesheets from the open archive (`EbookContent`), or a 404. The page's Content-Security-Policy allows only the app's own style and script by a nonce made per open; nothing is cached, navigation, new windows, downloads, permissions and external schemes are refused, and the context menu keeps Copy and Select all. `reader.js` and `reader.css` (embedded in the app) report the page in view (the last marker above a reading line), find text, mark search terms with the CSS Custom Highlight API, and pass links, selection, keys and zoom to the app as web messages.

### Online-only files

Files in OneDrive and other cloud-files folders are always indexed, which downloads each as the queue reaches it. Local files go first, and online-only files wait while downloading the next would leave less than 2 GB free. Once a file that was online-only has been read by every stage that reads files, Bibliotaph returns it to online-only with `CfSetPinState(CF_PIN_STATE_UNPINNED)`, which is what Explorer's "Free up space" does; content, path and timestamps don't change. A file the user pinned to the device, one open in the reader, or one the platform refuses stays. This lets a library larger than the disk be indexed in turns, and Settings can switch it off. `CloudFiles`, behind `ICloudFiles`, is the only caller of the cloud files API. Sync apps that stream through their own drive and cache rather than placeholders are left alone.

### Stages

Each stage has its own status per document (pending, running, complete, partial, blocked, failed, skipped) and a version; bumping a version re-runs that stage, and only that one, everywhere.

1. **Fingerprint.** SHA-256; a known hash attaches the path to the existing document and stops. ZIPs are listed here.
2. **Probe.** Page count, protection, permissions, page labels, outline, embedded metadata, capabilities. An e-book is cut into pages here.
3. **Text.** Per-page text and text quality; pages with no or garbage text are flagged for OCR. The book is searchable from here.
4. **Covers.** A PDF's first or chosen page, an image itself, or an e-book's cover image.
5. **Rule hints.** Folder names, the file name and the PDF's own information become provisional assertions (see Metadata).
6. **OCR.** Flagged pages only, page numbering kept.
7. **Match.** Fingerprints each page from stored text and finds copies and new versions (see Copies and versions), then checks the book against the user's tags (see User tags).
8. **Classify.** Has the AI read the book, when AI is set up and on (see Metadata).
9. **Chapter scan.** Once Classify is done, has the AI read the whole book a batch of chapters at a time (see Whole-book scans).

Stages 2 to 6 read the file; Reprocess runs them again while the old text stays searchable. Match and Classify read only stored text, wait for the book's OCR, and backfill existing libraries without opening a PDF.

### Job queue and lanes

A `job` row in `index.db` per document and stage holds priority, attempts, not-before time, lease and stage version, unique by content hash, stage and version, so enqueueing is idempotent. Stale leases return to pending at startup. Opening a book moves its pending jobs to the front.

Jobs run in three lanes, each with its own concurrency and pause: Index (probe, text, covers, hints, match), OCR (slow, so it never holds up the next book's text) and Classify (one book at a time, with chapter scans at the lowest priority). A failure retries with backoff; disk-full or credential failures block the lane with one visible notice. While a model server isn't answering, Classify jobs wait and the lane retries every minute rather than failing; a book the server fails on while it still answers other requests fails alone.

## Books, copies, versions, packs and parts

**Copies and versions.** Match fingerprints each page as lowercase letters and digits, dropping lines that repeat on half the pages (running heads, per-buyer watermarks). A document with the same page count and every fingerprint equal (at least 3 pages, and at least half, fingerprinted) is the same book, and its card joins the older one as a copy. User values come along; a single-value field the two confirmed differently is set aside for a "Copies disagree" card. Otherwise a file sharing at least 60% of its pages with a book, or failing that its title and publisher, is proposed as a new version. Same book in Select mode joins cards by hand the same way. An entry with several sources has one current source, which opens; when its files are all gone the newest copy with a file opens instead.

**Places across versions.** Binder items, page notes and reading places point at page ranges on a document. In another copy or version, `PagePlaces` finds each by its first and last page fingerprints once that version has them; a place not found opens at the same printed page marked "This page changed: check it", and Needs review lists them per version with Use this page.

**Packs.** A folder or ZIP of 20 or more images and no PDF becomes one card, named after it, unless the user split it; 5 to 19 images, or images beside PDFs, are proposed instead. Each member keeps its own entry, pointing at the pack as its parent. The decision is kept by path and follows the folder or ZIP when it moves. Pack together makes or merges packs by hand, through the same join records, so Undo works the same way; a pack made by hand can hold PDFs too (never a PDF with parts), and their pages are found under the pack. **Each file** is a query-time view, not a projection: with `LibraryFilter.PackFiles`, `LibraryQueries` reads its cards from `entry_doc` with each pack's row replaced by a row per `entry_member`, carrying the pack's `entry_id` (so `entry_meta`, facets, scopes and `entry_fts` apply as to the pack) with the file's `document_id` and its own entry as `pack_file`, which tells cards apart and owns the file's page hits. Members stay out of `entry_doc`, so Needs review and the counts outside the Library still see only packs. A pack's cover is a mosaic of its first four files unless the user chose one: `entry.cover_entry_id` names that member's entry, which follows the file through rescans and moves. The projection writes it to `entry_doc.cover_member` only while that member is in the pack with a file, so a file that leaves gives the card its mosaic back at the next projection rather than a dangling cover.

**Parts.** An adventure inside a compilation can be a card of its own: an entry of kind Part whose sources are page ranges in each copy of the file, one span each, never overlapping. The file is never split. Parts come from the reader's bookmarks or a page range, or from proposals. A proposal needs the book's own statement that it is a collection of separate adventures, found on its description pages (those before the first adventure, within the front matter, and the back cover), because campaign books print a level blurb at the start of every chapter. `PartRules` finds that statement with patterns ("a collection of five adventures", "one-shots", "each can be run on its own", with linking words such as "form a campaign" ruling a sentence out) and the starts from bookmarks and adventure blurbs ("for four characters of 3rd level"). When AI is on and the rules proposed nothing, the model reads the description pages too and must quote the statement before picking among the same bookmark candidates; the check wants that quote on a page the model was shown and about several separate adventures (`PartRules.DescribesCollection`), and each adventure's quote on its own pages. The statement is stored with the proposal and shown on its Needs review card. A blurb's quote takes in the party size written around it ("four to six 5th-level characters"), which `PartRules.Party` reads back, so accepting suggests each adventure's levels and players with the blurb as evidence; an adventure marked by hand gets the same suggestions, with origin rule, from the blurb on its first two pages (`PartRules.ReadBlurb`). A proposal never makes cards until accepted. A part inherits the file's system, edition, publisher, series, year and setting as values of its own source, never over what the user set on it, and is classified on its own pages. `PartsService.FollowAsync` finds each part again in every copy and version by its first and last page fingerprints. Browsing lists parts inside their file, whose card counts them; a search lists a matching part as a card of its own, in place of its file when both match, and More filters can show parts as cards while browsing or hide them. In Inside documents, a page is listed under the part it falls in, else under its file.

**Owned elsewhere.** A book owned in print or on a virtual tabletop is an entry with no sources, cataloged by the user's own values, with an Also own field naming where. A file whose title matches such a book, with no publisher that says otherwise, gets an "Is this its file?" card; accepting joins them.

**Check a download.** Hashes a folder or ZIP against the library without adding anything: a known hash is Already owned; other PDFs are read in the index worker and their page fingerprints and hint title and publisher compared as Match would. Nothing is written to either database or the queue.

## Search

- **Parser.** A hand-written parser in Core turns `chase "through a city" type:adventure level:3` into a query tree. Errors carry a position, so the box can underline the bad token and keep the query. One field list in Core serves the parser, its errors and the search field guide under the box. Values are always bound as parameters; the FTS5 `MATCH` string is generated from the parsed query with every term quoted, and column names come from a fixed list.
- **Documents tab.** `entry_fts` over title, subtitle, publisher, series, authors, tags, notes and effective metadata, with bm25 column weights; confirmed and provisional values sit in separate columns, so confirmed ones rank higher. Words also match the file names of images in packs.
- **Fields.** Text fields (`title:`, `publisher:`, `author:`, `series:`, `tag:`) match `entry_fts` columns. Term fields (`system:`, `edition:`, `type:`, `setting:`, `style:`, `theme:`, `environment:`, `duration:`, `own:`, `store:`) match a vocabulary term by key, label or alias through `entry_facet` and `term_alias`, with `*` prefixes. `setting:`, `theme:` and `environment:` also match the `inside:` facets a whole-book scan projects from `chapter_tag`, and `creature:` matches only those. `level:` and `players:` match overlapping ranges. `favorite:`, `collection:`, `where:` (here or elsewhere), `format:` and `folder:` filter by marks and places. Any field takes `unknown` and `-`.
- **Inside documents tab.** `page_fts` over page text, with `snippet()` quoting the page; hits are grouped and limited per book in SQL. Highlights aren't stored: opening a hit runs find on that page in the viewer worker.
- **Facets.** Counts are `GROUP BY` over `entry_facet` for the current results, leaving out the facet's own dimension. Levels are ranges per system; unknown is a real value.
- **Coverage.** While books are still being read, results say "Searching text in N of M documents".
- **Saved searches.** A saved search stores the search text, scope, filters, order, layout and tab as versioned JSON, never a list of books, so opening it runs the search again.
- **Ask.** A mode of the search box that has the AI turn a plain-English request into ordinary search terms. `PlainSearchPrompt` sends only the request (cut to 500 characters, in guarded tags) and the vocabulary's names; the answer can only fill a schema of field filters and words. `PlainSearchCheck` drops any field the box doesn't have, any vocabulary value that isn't a term, and any word that isn't the user's own; every kept piece must parse with the box's own parser, and every change is explained. The pieces show as editable chips, and nothing runs until the user presses Search, which puts them in the box as query text.

## Viewer

`Bibliotaph.Viewer` is built so a page never waits for a full-quality render.

1. **Preview first.** A render at a quarter of the target scale shows first, replaced by the full render. Scanned pages, whose whole image decodes at any scale, preview from cached page thumbnails.
2. **Prefetch and cancel.** Two pages ahead in the scroll direction; requests for pages scrolled away are dropped.
3. **Tiles.** Above 200%, or for very large pages, 512-pixel tiles with a memory budget.
4. **Labels.** "Printed p. 42 · PDF page 46 of 180"; where a book was left is kept apart from search jumps.
5. **Selection and copy.** The worker returns character boxes with each page; OCR'd pages select against stored word boxes. A PDF that forbids copying disables Copy with the reason.
6. **Thumbnail strip.** A virtualized strip of every page, drawing only those in view and four either side, from memory, then the `cache\pages\` thumbnails, then an idle render lane that runs only while no page render waits. Pages with notes have a badge; a binder item's pages have a bar.
7. **Links.** Link annotations are read when the pointer reaches a page; page links jump with Back, web links open in the browser after asking (http, https, mailto). A contents or index page with no links of its own gets links made from the printed page numbers it lists (`PageReferences`), mapped through page labels or, failing that, through the page numbers printed in the book's own text; with neither, no links are made, since a wrong jump is worse than none.
8. **Windows.** Any number of pop-out reader windows, each with its own viewer worker up to the cap. A binder's reader opens the next item's book ahead of time on the same worker and draws its first page, so Next shows it at once.

JPG, PNG and WebP open in an image view with zoom and pan, decoded at a capped size; WebP uses Windows' own decoder. An e-book opens in the e-book reader (see E-books).

## Metadata and classification

### Effective values

`EffectiveMetadata` (Core) computes each field from its assertions, never storing the result. Origins rank user 100, folder rule and user tag 60, AI 50, rule 30, embedded 20, folder 15, file name 10. For a single-value field the latest confirmed value wins and is never replaced by a suggestion; otherwise the best-ranked suggestion applies and the rest are alternatives. For a multi-value field the value is every confirmed value plus the top origin's suggestions that arrived after the user's last decision there. A closed field needs review when an alternative arrives after the last decision. Rejections (entry, field, normalised value) suppress a value from every origin, including later models. Every decision, bulk edit and correction is undone from a snapshot of the field's assertions and rejections.

### Rule hints and folder rules

Hints run on every file: a folder name counts only when it matches a vocabulary term or alias (each such folder label can be switched off), the deepest folder wins a single-value field, an edition implies its system, junk embedded titles are skipped, and levels and party sizes are read from the file name, title and subject. Get it from comes from a store named in a folder name, file name, the PDF's producer or a watermark line; watermark lines (`Watermarks`, Core) are found in memory, matched against the store vocabulary and then dropped, never stored, logged or sent to a model. Re-running replaces earlier hints by diffing, so an unchanged suggestion keeps its age, and never touches a value the user decided.

When the user decides the same value for a field on three or more books directly in one folder, a folder rule is proposed; once accepted it suggests that value, with origin folder rule, for every file in the folder and below. After a correction, the details offer to repeat it on look-alikes: books in the same folder whose field shows exactly what the corrected one showed before.

### Needs review and vocabulary

`MetadataReview` (Core) decides the cards: a closed field whose sources disagree, a book with no usable title, and optionally every unconfirmed value. Copies disagree, new versions, packs, parts, folder rules, new terms, changed pages and correction requests have cards of their own.

Vocabularies (systems, editions, types, settings, styles, themes, environments, durations, stores, places owned) live in `catalog.db` as terms with aliases and parents, seeded from versioned starter sets. A name means one term per vocabulary. A term the model proposes that the vocabulary doesn't know becomes a pending term whose values are held back until the user adds, maps or rejects it. After a vocabulary edit, every book is projected and hinted again in the background.

### User tags

The user's own tags live in `catalog.db` (`user_tag`: name, comparison name, the words as JSON). `UserTagService` turns a tag's words into an FTS5 expression of quoted words (a word of three letters or more also as a prefix, as search reads it) and asks `page_fts` which cards' pages have any of them, through `entry_doc`, so an adventure counts only its own page range. A card whose words are on at least 3 pages and at least 5% of its pages with text (`UserTagRule`) gets a provisional `tags` assertion of origin user tag, with the words as its quote and up to 12 of the pages as evidence. Saving a tag replaces its guesses across the library as rule hints are replaced: a guess made again keeps its row and age, and decided rows and rejections are never touched. Deleting a tag removes its undecided guesses. Match, once a book's text and OCR are in, checks it against every tag, and Forget its text removes its undecided guesses. Tag definitions stay on each PC; the tags on books travel with the metadata decisions.

### Classification

- **Input.** An excerpt of about 24,000 characters: the first pages with text, the back cover, contents pages, the introduction, then pages sampled evenly, each after a `[Page N]` marker, with watermark lines removed. The system message holds the rules, field definitions and the vocabulary's names, and nothing from the book. The user message holds the file name, up to three worked examples (the user's own confirmed values on similar books, never book text) and the excerpt inside `<book-excerpt>` tags. A library folder can be kept from AI.
- **Output.** A JSON schema with one array per field, each item `{value, page, quote}` and nothing else; an empty array is unknown. Every string has a `maxLength` (a value 200 characters, a quote the evidence check's 400), here and in the chapter and adventure schemas, because the schema's grammar otherwise lets a model write on inside one string until it hits the answer cap (the built-in AI's 2,048 tokens). Tags are never filled by AI. The field list in `ClassifierPrompt.Fields` drives the schema, parsing and evidence check.
- **Evidence check.** A claim stands only if its quote appears on the page it cites (compared as letters and digits after normalisation, at least 8 of them) and, for printed values such as title, publisher, year, levels or system, the quote names the value. Values must parse and closed fields must resolve through the vocabulary. Kept claims become provisional AI suggestions; the user's values always win.
- **Untrusted text.** Book text goes only in the delimited data block, with anything that looks like its closing tag or a page marker altered. The client exposes no tools, keys outside the schema are ignored, and nothing in an answer can change a setting, a tag or a user decision. Logs get counts and reasons, never book text or quotes.
- **Runs.** Each run records provider, model, prompt and schema version, content hash, pages read and outcome in `classification_run`. Changing model or prompt never reclassifies by itself; Settings offers to.
- **AI reading.** A page shows the book being read, the answer's fields as they stream in (parsed from unfinished JSON), and what the evidence check kept and dropped, from an in-memory feed of the last 20 books.

### Whole-book scans

Classification reads a sample; the Chapter scan stage (`ChapterScanStage`, Processing) then reads every page, when Scan whole books is on. A book is split into chapters from its top-level bookmarks, else the entries of its printed contents page, else runs of about 25 pages, and chapters are read in batches of about 20 to 30 pages, one request per job, the job going back to the queue between batches so a book waiting to be catalogued goes first. It waits for the book's OCR and Classify, skips folders kept from AI, and never runs while a person is waiting on the model: `ModelActivity` cancels its request the moment cataloging, Ask or a test starts, and it waits for half a minute of quiet before going on. The answer names each chapter's settings, environments and themes as vocabulary terms and its creatures by name, each with a page and quote that must be on that page inside the chapter. Progress is saved in `catalog.db` (`chapter_scan`, by content hash) after every batch, so a scan carries on after a restart, and survives an index rebuild (`ChapterProjection` restores `chapter` and `chapter_tag` at startup). Findings never become assertions: they reach search only as `inside:` facets, and a book's own values are never touched. Scan again, or a changed file, reads the book again.

### Model access

One client over `HttpClient` and System.Text.Json, with no SDK. Ollama is asked through `/api/chat` with the schema as `format`; other servers through `/v1/chat/completions` with a strict `json_schema` response format, falling back to `json_object`. Answers stream. When an answer that must be JSON stops at the token limit (`finish_reason` or Ollama's `done_reason` is `length`), the client throws `ModelAnswerCutOffException` with what was written. `ModelClassifier` keeps the items the model finished (`PartialAnswer.Close` cuts back to the last complete value and closes the JSON) and reads them through the evidence check; with none, or for a chapter batch, the book or batch fails alone, without the server check a failed request gets. A prose answer that runs out is returned as it is. An endpoint off this computer's network needs an explicit "Send excerpts to this server", and an API key goes to Windows Credential Manager.

**Built-in AI.** Bibliotaph ships llama.cpp's `llama-server` (the Vulkan build, which falls back to the processor) in `aiworker\`, pinned by release and SHA-256 in `build/engine.json`; a build without it downloads and verifies the same pin into the data folder. `BuiltInEngine` starts it on first use on 127.0.0.1 and a free port with a one-time API key, one request at a time, waits for `/health`, and talks to it through the same OpenAI-compatible client. The context starts at 16K tokens and grows when a book needs it. It stops after 5 idle minutes, when the Classify lane pauses, when AI is switched off or moved to a server, and with the app; a job object ensures it never outlives the app. Models (Qwen3 4B, 8B, 14B and 30B-A3B, Phi-4 mini, Llama 3.1 8B, Granite 3.3 8B, Mistral Small 3.2 24B) are pinned to a Hugging Face revision, size and SHA-256, downloaded only when the user asks, resumable, and renamed into place only once the hash matches; only pinned models are offered. `GraphicsMemory` reads adapter memory from the driver's registry values to group the list by what fits and to suggest Qwen3 8B or 4B, the models the classifier was tried with. A `.gguf` file of the user's own is stored as its path and used in place, never deleted. Runs on the built-in engine count as a different model from the same one on a server. The embedding model for Ask (nomic-embed-text v1.5, Apache-2.0) is pinned and downloaded the same way, and runs in a second `BuiltInEngine`.

### Ask this book

A panel in the reader answers questions about the open PDF from its pages.

- **Retrieval.** The question's words (stop words removed, as quoted FTS5 prefixes) against `page_fts`, and, with an embedding model set, the question's vector against `page_vec` by cosine; the two rankings are fused by reciprocal rank, with a small boost for pages under a matching bookmark, and pages whose text reads like an index, contents or glossary (dot leaders, short lines ending in page numbers, or mostly page numbers) keep half their score. A weak-signal guard says the book doesn't cover the question rather than choosing evidence: words count when the best page by words has half the question's weight, each word weighing one over the number of the book's pages with it, and meaning counts when the best page is close and stands out. Up to 8 pages (24,000 characters) become the evidence. Page vectors are filled in the background when the book is opened in the reader, or on first ask. Chat requests ask the model not to think (Ollama's `think`, or `chat_template_kwargs.enable_thinking` for OpenAI-compatible servers), dropping the switch for a server that refuses it.
- **Answer.** The chat model gets rules in the system message and the pages in the same guarded excerpt block as classification. `AskAnswerCheck` checks the answer as it streams: citations to pages that were sent become links, others are removed and their sentences marked, and each quotation is looked for on its cited pages and shown unquoted when it isn't there.
- **Conversations.** Turns are kept in `catalog.db` (`ask_turn`, the last 50 per book), so a rebuilt index keeps them. A follow-up is first rewritten to stand alone from the last three turns, without any book text. "Forget its text" forgets the conversation too.

### Ask your library

**Answer from my books** in the search box's Ask mode answers a question from pages across the library (`LibraryAskService`, Processing; `LibraryAskQueries`, Index).

- **Scope.** Each `AskFilter` becomes a `PageScope` (whole documents, or page ranges of them), and the question reads the pages every filter allows. Today's filter, `BookFilter`, is the Library's filter panel and the search box's fields (its plain words dropped), as the Library last ran them (`LibraryAskScope`); `LibraryQueries.GetPageSpansAsync` turns it into each PDF's pages, or an adventure's own range. A filter on chapter tags would add page ranges the same way. Only documents a card shows count, and documents in folders kept from AI are left out of the scope and checked again before any page is used.
- **Retrieval.** Ask this book's ranking at library scale: words through `page_fts` within the scope (100 deep), meaning by streaming the scope's vectors past a top-k `MeaningRanking` (the library's vectors aren't held at once), reciprocal-rank fusion with the bookmark boost and the list penalty, then `CapPerBook` keeps at most three pages a book before choosing up to 10 pages (3,000 characters each, 24,000 in all). The weak-signal guard weighs words by how rare they are across the scope and compares the best cosine with the scope's median; when it fires, no model is asked and the closest pages are named.
- **Answer.** `AskPrompt.LibrarySystemMessage`, with each page's book title in the guarded block and a marker of book number and page ("2:112"), so a bare page number the model invents never names a page sent. `AskAnswerCheck` checks it as for one book, against each page's place in the evidence, and citations become the book's title and page, with the document they open (`AnswerPart.DocumentId`). There is no conversation.
- **Reading the library for meaning.** `LibraryVectors`, a hosted service, makes page vectors book by book with Ask this book's fill code and storage (`page_vec`), in document order, a minute after start. It gives way between batches while `AiUse` says the user is asking anything of the AI (and for 30 seconds after) or a book opened in the reader wants its vectors, backs off five minutes when the model fails, and needs no queue of its own: what it made is in `page_vec`, so after a restart it carries on with the first book still missing some. `ai.embedding.library` ("False") switches it off; Settings > AI shows its progress in pages.

## Online libraries

Bibliotaph reads the libraries of online services (D&D Beyond, Demiplane) and stores (Humble Bundle, DriveThruRPG, which also serves DMs Guild) so the books owned there become cards owned elsewhere.

- **Browser.** `OnlineBrowserWindow` hosts WebView2 with one profile for all of Bibliotaph's windows in the data folder's `browser\`, so sign-ins last between visits and stay apart from the everyday browser. It opens the service's library page and never navigates, clicks or scrolls by itself. After each page settles it takes the page's HTML and offers Read this page when a reader recognises it. Bibliotaph stores no password; Sign out of all services clears the profile through WebView2. Pop-up windows a page opens are hosted by Bibliotaph too, so sign-ins and downloads work.
- **Readers.** One `IOnlineLibraryReader` per service turns a page into books (title, link, publisher, type, system, year, cover address) and fetches nothing. D&D Beyond's reads the Next.js data its page carries; the others read markup cut at each book's card. A reader also says where a book's link goes: Also own for a service whose books are read online, Get it from for a store whose books are files to download.
- **Imports.** `OnlineImports` previews what a page would change: a link already on a card updates only its empty fields, a card with the same title gets the link, anything else is new, and a whole-library page also lists linked books it no longer shows. Ticked rows are written in one transaction as the user's own confirmed values, with Undo. Covers are only images the page already loaded (or a saved page's files), never fetched.
- **Online reader.** A book owned only online opens in a reader built around the service's own page, with the same profile, so it is signed in. It follows links on the book's site and its sign-in sites; anything else goes to the everyday browser. It copies no text from the page, so it has no search, notes on pages or Ask. An optional reading-mode stylesheet per service hides the site's chrome. A page can be added to a binder by its address.
- **Downloads.** A download the user starts on a store's page is saved into a downloads folder inside a library folder, under a free name, by the browser; the folder is then scanned and the file read like any other, so "Is this its file?" offers it to its book.
- **Site icons.** Fetched once per site into the cache for the cover badge, unless switched off.

There is no automation: Bibliotaph acts on a service's site only through the user's own clicks.

## Collections, saved searches and binders

Favorites, collections (nested to any depth, holding entries), saved searches and pins are rows in `catalog.db`, projected into `entry_scope` so search and the Library's scope can use them. Joins move a book's heart, collections, pins, notes and binder items to the card it joins, and "Not the same book" moves them back. `FolderCollections` proposes folders of three or more books as collections in Needs review, skipping folders named only by vocabulary terms; `collection_folder` keeps each answer by library folder id and relative path, and a linked collection gains the books new to its folder after each hashing pass until `CollectionsService` sees a change by hand. `CollectionSuggestions` proposes books for a collection that share its most common series, or setting and system (held by 60% of its own books and at least three); `collection_decline` keeps each Never by collection and book.

A binder (`session_pack` in code) is an ordered list of items in named sections, each a whole book, a page range (`page_ref`) or a page of an online book, with a label and note. Opening a binder shows its reader: the items down the left, the book in the middle, the binder's notes on the right, Next and Previous stepping between items. An item whose file can't be reached stays, dimmed, saying why. A binder can be kept at hand during games, optionally for a game system, and then shows in every other binder's reader to open a page in a window of its own.

Notes are a book's own note and notes on page ranges; they are found again in other copies through `page_ref` like binder items, and search reads them through `entry_fts.notes`.

## UI shell

- **MVVM.** CommunityToolkit.Mvvm source-generated view models; services from the generic host's DI container. Long-running work is hosted services in Processing.
- **Navigation.** Routes for Home, Library, Collections, Binders, Needs review, Settings, the reader, the online reader, Check a download and AI reading. A back stack restores search, filters, selection and scroll position when leaving the reader. The sidebar's Pinned group lists pins in order, reorderable by drag or Alt+Up and Alt+Down. Reader windows and a binder can pop out into windows of their own.
- **Theme.** The design's colour tokens are brushes in Light and Dark dictionaries, following the Windows app mode unless overridden, plus a Contrast dictionary built live from the system colours under a Windows contrast theme. DM Sans for the interface and Libre Caslon Display for display headings, both embedded; Lucide icons as geometry resources. Animations are off when Windows' animation effects are.
- **Library.** The cover grid uses `VirtualizingWrapPanel`, with covers decoded off the UI thread at display size and frozen. Filters show as chips; Select mode drives bulk edits, Same book, Pack together, Remove adventures, collections and export.
- **Accessibility.** Per-monitor DPI, automation names on every control, a keyboard path for every action, and Ctrl+/ to list shortcuts (Ctrl+K search, Ctrl+F find in book).

## Web server

bibliotaph.online is the same library for game masters whose books are in cloud storage. A server holds each user's catalog and index and reads their books from their storage; it never keeps a copy of a book. It is being built in steps; the first gives it its host, accounts and browser app.

**Host.** `Bibliotaph.Server` is an ASP.NET Core app that also serves `Bibliotaph.Web`, a Blazor WebAssembly client, from the same origin, so the browser holds no tokens: a cookie session does (the backend-for-frontend pattern). `/auth` is navigated to, `/api` is called with JSON, and every other path returns the client's page so its router can take over. `Bibliotaph.Web` copies the Windows app's look rather than reinventing it: its stylesheet comes from the mock-ups the WPF theme follows, its fonts are the app's, and its icons are read at run time from the app's own `Icons.xaml`.

**Sign-in.** OpenID Connect with Microsoft (any work, school or personal account) and Google, asking for `openid profile email` only, code flow with PKCE. Each provider's callback is `/auth/callback/<provider>`. `/auth/complete` maps the provider's stable subject (Microsoft's `oid@tid`, Google's `sub`) to an account: a known sign-in signs in, an unknown one links to the account already signed in or redeems an invitation, and anything else is refused as invite-only. The session cookie is `__Host-bibliotaph`: HttpOnly, Secure, SameSite=Lax, sliding over 14 days; API calls get 401 rather than a redirect. Every API write must carry the `X-Bibliotaph` header, which a cross-site form can't send. A strict content security policy allows only the site's own scripts, styles and WebAssembly, so the client has no inline styles. Signing in with a storage provider is kept apart from signing in to Bibliotaph: storage connections have their own grants and tokens.

**Accounts.** `accounts.db` (EF Core, its own migrations) holds `users`, `logins` (provider and subject to user), `invites` and `storage_connections`. An invitation is a one-time link whose code is 18 random bytes; only its SHA-256 is stored, and it lasts 14 days. The first admin's invitation comes from the server's own `invite` command, which `infra/invite.ps1` runs inside the container.

**Each user's library.** Every user gets `/data/users/<id>/catalog.db` and `index.db`, the same databases and code the Windows app uses, so migrations, stores and search behave identically. `LibraryServices` builds each open library its own service provider with the Windows app's registrations from `Bibliotaph.Processing` (stores, `JobBoard`, `IndexingService`, scanning and hashing), so nothing is shared between users; what the Windows app gets from Windows is replaced: the source lister, file reader and folder watcher by OneDrive's, WPF's image codec by Skia (`SkiaImageCodec`), and file IDs and cloud-file states by stand-ins that have none. `UserLibraries` opens a user's library on first use (restoring, migrating the catalog, starting its index writer and indexing), counts leases so requests share one opening, and closes it after 20 minutes idle, unless it is still scanning or has files left to read.

**Reading books on the server.** The server runs the Windows app's Probe, Text, Covers and Rule hints stages (OCR and AI come later). PDFs are read by the same `Bibliotaph.PdfWorker`, built for plain .NET on Linux (without Windows OCR) and published into the image's `pdfworker/`; one worker process, shared by every library in turn, keeps a crash or a runaway PDF away from the server, and on Linux `MemoryWatch` reads the worker's resident memory from `/proc` and kills it past the cap, as the job object does on Windows. A book on a drive is fetched once to be read: `SourceFiles` treats it like a file in a ZIP (`IRemoteFiles`), streaming it into the extract cache under its content hash and checking that hash, and the job board leases a book's next stage before the next book's first (`bookAtATime`), so its stages read the one copy. The copy is deleted as soon as none of its documents has a file stage waiting, the cache is capped at 1 GB as a backstop, and the folder is emptied whenever the library opens or closes. Hashing downloads each new file once more, to a temporary file deleted on close.

**The library in the browser.** `GET /api/library` runs the Windows Library's query on the user's library (`LibraryQueries.ListAsync`, or `SearchDocumentsAsync` and `SearchPagesAsync` with a `SearchPlan` from the parsed search), with the filter panel's menus counted each without its own choice, and returns cards rather than index rows: every word a card or a matching page shows comes from `CardText` in `Bibliotaph.Index`, which the Windows app's view models use too, so the two can't drift apart. The fixed menus and their labels are in `LibraryChoices` in `Bibliotaph.Api.Contracts`. Covers are served from the user's cover cache by name (`/api/library/covers/{name}`), cached by the browser for a year since a cover's name changes with its image (a book owned elsewhere's is revalidated). The page draws its cards in batches as the end of them scrolls into view, and keeps its search and filters in its address. `GET /api/library/books/{entryId}` gives a book's details as the Windows inspector builds them, from `LibraryQueries.GetDetailsAsync`, the effective metadata and vocabulary, the locations, copies, parts and pack files; the words come from `DetailsText` (Processing) and `FieldText` (Core), which the inspector's view models use too, and a location reads as the drive and its folders. `GET /api/home` gives Home's two rows.

**Covers across restarts.** The server's disk is ephemeral, so each library's `CoverMirror` keeps its cover cache in Blob storage (container `covers`, keys `users/{id}/{name}`): it lists what is kept when the library opens, uploads what is on disk and not yet kept, watches both cover folders for new covers, and on a miss the cover endpoint fetches the cover back before serving it. Without a configured container (tests, a developer's machine) covers stay on disk only.

**Storage connections.** Connecting OneDrive is its own OAuth flow (`/storage/connect/onedrive`, callback `/storage/callback/onedrive`, PKCE), on the same app registration as Microsoft sign-in but with the scopes `offline_access Files.Read Files.ReadWrite.AppFolder`, and it never signs anyone in. `storage_connections` keeps the drive's ID and kind, the refresh token encrypted with Data Protection, a per-connection notification secret and the change subscription. `DriveTokens` turns refresh tokens into access tokens, kept in memory until shortly before they expire, saves rotated refresh tokens, and marks a connection Needs reconnect on `invalid_grant`. Graph is called over REST by `Bibliotaph.Storage.OneDrive` (no Graph SDK), which retries 429, 503 and 504 after Retry-After.

**OneDrive library folders.** A library folder on a drive is the path `/onedrive/<drive id>/<path in drive>` (`DrivePath`), so `SourceRoot`, relative paths and moves work unchanged. `OneDriveSourceLister` walks a folder with one children call per folder, skipping nested library folders, and treats any failure as the folder being unreachable so a half listing never reads as deleted files. `OneDriveFileReader` downloads a file whole to `/data/downloads` (readers seek) with delete-on-close; the folder is emptied at start. `DriveNotifications` subscribes to each drive's root (`/me/drive/root` for personal drives, `/drives/<id>/root` otherwise) for up to 42,300 minutes, with `clientState` = connection ID and secret; `/storage/notifications/onedrive` echoes Graph's validation token and otherwise checks the secret in constant time and queues a scan of that user's folders on that drive, answering 202 at once. `DriveWatch` renews subscriptions due within three days, twice a day, and opens every connected library so changes missed during a restart are found. Subscriptions are made only when `PublicOrigin` is a public https address.

**Durability.** The server runs as exactly one Container Apps replica, never scaled out or to zero, because each SQLite file must have one writer. Its disk is only a working copy: Litestream, which starts the server as its child process, streams every database's WAL to Blob storage within a second. At start it restores `accounts.db`; a user's databases are restored from the replica when they first open (`LitestreamRestore`), and Litestream's directory watch picks up new and restored files without a restart. Data Protection keys (the cookie keys, and later the encrypted storage tokens) are kept in Blob storage, wrapped by a Key Vault key, so sessions and secrets survive a new container.

**Azure.** `infra/setup.ps1` creates or refreshes everything in `rg-bibliotaph`: a user-assigned identity the app runs as (Blob, Key Vault and registry pull rights), the storage account, the Key Vault with the key-ring key and the sign-in secrets, the Microsoft app registration with both callbacks, the container app in an existing Container Apps environment, the custom domain with managed certificates, and a deploy identity GitHub Actions signs in as through OIDC, with no stored secret. CI builds the image on Linux for every pull request and checks it starts; a push to main that passes the Windows build and tests pushes the image to the registry and rolls the app onto it.

## Safety and secrets

- **Source files.** Bibliotaph never writes to a source file: one read-only reader, a banned-API analyzer, and worker processes that open files read-only. The one exception is returning a file indexing downloaded to online-only, which changes no byte, name or timestamp and is confined to `CloudFiles`. Browser downloads are written by WebView2 into the chosen downloads folder, never by Bibliotaph's code.
- **Passwords.** A PDF password can be remembered, keyed by content hash so it survives moves and covers copies, which lets the index worker read that book unattended; otherwise it is kept in memory for the session. A file that forbids copying is still indexed, with Copy off in the reader. A PDF whose security handler PDFium can't open is marked Protected, keeps editable details and offers Open in another app.
- **Secrets.** Saved PDF passwords and API keys go to Windows Credential Manager (`Bibliotaph:pdf:` and `Bibliotaph:ai:` targets), local to the machine; never in the databases, logs, exports, backups or prompts.
- **Forget its text.** A flag on the document stops indexing it; its pages, FTS rows, vectors, outline, jobs, cover, thumbnails, AI runs, undecided suggestions and Ask conversation are removed. "Read it again" clears the flag.
- **Logs.** Rolling Serilog files in the data folder's `logs\`; page text, prompts, requests and passwords are never logged, only counts and reasons.

## Backup, restore and library sync

**Backup.** A zip of a `VACUUM INTO` copy of `catalog.db`, optionally `index.db`, and a `manifest.json` (app version, catalog schema, library folders, counts). One is made on demand and one automatically each week, keeping the last four automatic ones. Restoring stages the zip (an older catalog is migrated, a newer one refused), lets the user point moved library folders to their new place, and swaps the catalog in at the next start before any database opens, keeping the old one beside it. Machine-specific data (volume serials, file IDs) is cleared, and the index is rebuilt without hashing files again when the backup carried it. Export writes a CSV of the books or JSON of every catalog table.

**Library sync.** A folder the user picks (in OneDrive, say) holds one JSON file per PC, `Bibliotaph sync\<PC name>.json`; each PC writes only its own and reads the others'. Records travel by stable keys: books by content hash (with other copies' hashes as aliases), everything the user made by a `sync_id` GUID. What travels is the user's work: metadata decisions per field, hearts, notes, collections, saved searches, binders, pins, vocabulary terms, "Not the same book" answers and books owned elsewhere. Library folders, reading places, settings, AI runs, whole-book scans, chosen covers, caches, `collection_folder` (a folder is one PC's) and `collection_decline` stay on each PC, and library files are never touched. `SyncMerge` (Core) merges per field, the newer change winning and deletions winning over earlier changes through kept tombstones; it is idempotent. `CatalogWrites`, an EF Core interceptor, notices writes to user-work tables and has this PC's file written shortly after. Work on a book this PC doesn't have waits until a file with that hash appears.

## Packaging, releases and updates

- **Installer.** Velopack, per-user with no admin, self-contained win-x64: the app and the PDF worker in `pdfworker\` each carry .NET, and the AI engine sits in `aiworker\`. The pack id `BibliotaphApp` installs into `%LOCALAPPDATA%\BibliotaphApp`, which uninstalling deletes, deliberately apart from the user's data in `%LOCALAPPDATA%\Bibliotaph`. `Program.Main` runs Velopack's hooks before anything else. The installer is unsigned for now, so Windows shows "unknown publisher". It is to be signed through SignPath Foundation's free certificate for open source projects (decided 2026-10-11), so the publisher shown will be "SignPath Foundation": the release workflow sends only Setup.exe to SignPath's GitHub Action and a maintainer approves each request. The launcher stub and Update.exe that `vpk pack` generates, and third-party binaries, stay unsigned. The README's "Code signing policy" section holds the roles and privacy statement SignPath requires.
- **Releases.** A `vMAJOR.MINOR.PATCH` tag runs the release workflow, the only one with write access: publish the app and worker at the tag's version, generate licence notices, download the latest published release so `vpk pack` makes a delta, wait for CI to pass on the tagged commit rather than running the tests again, and create a draft GitHub Release with Setup.exe, the packages and their feed, its notes taken from the version's CHANGELOG section. A maintainer publishes the draft.
- **Updates.** `UpdateService` checks the repository's published releases (never drafts or pre-releases) with Velopack's `GithubSource` at start and once a day, and downloads in the background. A ready update shows in the sidebar; Bibliotaph restarts to apply it only when the user clicks, closing the databases first, and an update not applied is applied at the next start. It is silent offline, on errors, and in builds that weren't installed. A fork's release build updates from that fork.
